Data Structures 03 / 08

FVectorNode 图节点结构

  • gref 辅助图表 row ref
  • tref 主表 row ref，搜索命中后回主表随机读
  • vec 预处理后的量化向量 (FVector)
  • neighbors[] 每层邻居列表：第 0 层最多 2M，其他层最多 M

FVector 量化表示

struct FVector { float abs2, subabs2, scale; int16_t dims[4]; // 动态长度 }; // 创建时：找最大绝对值 → 计算scale // → 每维float映射到int16 // 距离还原： float distance_to(FVector *other) { return abs2 + other->abs2 - scale * other->scale * dot_product(dims, other->dims); }

Insert Path 04 / 08

插入与分层构建

新节点层数按指数分布随机生成，从高层逐层搜索候选，每层选择邻居并更新反向连接

插入流程

// 1. 随机层分配 double log = -log(rnd()) / log(M); target_layer = min(floor(log), max_layer+1); // 2. 高层：仅保留1个最近入口 for (; p.layer > target_layer; p.layer--) search_layer(&p, vec, NEAREST, 1, &candidates); // 3. 目标层→第0层：搜索+选邻居 for (; p.layer >= 0; p.layer--) { search_layer(&p, vec, NEAREST, max_neighbors, &candidates); select_neighbors(&p, target, candidates, max_neighbors); } // 4. 更新反向连接 for (p.layer= target_layer; p.layer>=0; p.layer--) update_second_degree_neighbors(&p, target);

写入放大

  • 插入成本与 M、层数、ef_construction、图规模相关，不是固定 O(1)
  • 每个新节点可能导致多个已有节点的 neighbors blob 被更新
  • 保存新节点 → 写隐藏图表 ha_write_row
  • 更新邻居 → ha_update_row 修改 neighbors blob
  • 如果新节点层数高于 start，成为新的入口节点
  • 高并发写入时，重叠邻居节点易产生锁等待和死锁

// 维护两个队列 Queue<Visited> candidates, best; // 循环：弹出候选，扫描邻居 while (candidates.elements()) { auto cur = candidates.pop(); if (cur.dist > furthest_best && best.is_full()) break; // 剪枝 // 扫描邻居，按距离加入候选 for (links : cur.neighbors[layer]) if (!visited.seen(link)) { candidates.push(link); if (dist < furthest_best) best.replace_top(link); } }

Storage Design 06 / 08

隐藏辅助图表

MariaDB 为每个 VECTOR KEY 创建一个隐藏辅助表（后缀 #i#%02u），持久化 HNSW 图节点

CREATE TABLE i ( layer TINYINT NOT NULL, // 节点最高层 tref VARBINARY(N), // 主表 row ref (nullable for deleted) vec BLOB NOT NULL, // 量化后向量: scale + int16 dims[] neighbors BLOB NOT NULL, // 每层: <N><gref>...<gref>... UNIQUE (tref), KEY (layer) );
字段索引用途
layerKEY打开图时用 IDX_LAYER 找最高层入口
trefUNIQUE搜索命中后回主表；delete/update 定位
vec无量化向量数据，加载到内存
neighbors无每层邻居 gref 列表

Delete / Update 策略

  • 不是物理删除：辅助表 tref 置 NULL，内存节点标记 deleted
  • 第 0 层搜索跳过 deleted 节点；高层仍用 deleted 节点导航
  • UPDATE = 旧节点 invalidate + 新节点 insert
  • 长期 update/delete 会导致 tombstone 累积

Performance Impact 07 / 08

OLTP 性能影响分析

HNSW 把一次主表 DML 扩展成"主表变更 + 隐藏图表变更 + 内存图缓存维护"

写入路径关键点

  • INSERT：搜索图 + 写新节点 + 更新邻居 → 多次隐藏图表 I/O
  • UPDATE：等价于 delete + insert，旧节点 tref 置 NULL
  • DELETE：逻辑删除，保留在图中用于导航
  • 写路径在 handler 层执行，直接拉长事务持锁时间
  • 邻居更新未按 gref 排序，InnoDB 死锁风险存在

内存与并发

  • MHNSW_Trx：事务本地非共享 HNSW 上下文，大事务内存峰值
  • COMMIT：递增 version，失效共享缓存 → 后续查询需重新加载
  • mhnsw_max_cache_size 超限后 reset，同一事务继续访问又要重加载
  • SAVEPOINT ROLLBACK：reset 事务本地 HNSW cache
  • XA PREPARE：显式 XA 暂不支持

Key Takeaways

核心结论

架构特点

  • 主表 + 隐藏辅助图表 + MHNSW_Share 内存缓存 三层架构
  • 向量 int16 量化 + dot product 还原，平衡精度与速度
  • UPDATE/DELETE 采用逻辑删除，tombstone 会累积
  • 5 个 SQL 函数覆盖距离计算与格式转换

OLTP 注意事项

  • 单行事务写放大：主表 + 隐藏图表 + 邻居更新
  • commit 后共享图缓存失效，后续查询需重加载
  • 并发写入存在隐藏图表行锁竞争和死锁风险
  • 需要重点观察 lock wait、deadlock、P99 commit latency
