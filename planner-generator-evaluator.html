Planner – Generator – Evaluator 三智能体架构

受 GAN(生成对抗网络)启发的长时运行应用构建 Harness
来源:Anthropic Engineering — Harness design for long-running application development
整体架构:一句话需求 → 完整全栈应用
用户输入
1–4 句自然语言描述
如「做一个 2D 复古游戏编辑器」

① Planner
规划者
把一句话扩展为完整产品 Spec
➜
GAN 式生成–评估迭代循环(可多轮)
② Generator
生成者 · 写代码
  • 按 Sprint 逐特性实现
  • React + Vite + FastAPI + SQLite
  • 每个 Sprint 结束先自评
  • Git 做版本控制

评估者 · QA 把关

  • 像用户一样测 UI / API / 数据库
  • 按评分标准逐项打分
  • 任一维度低于硬阈值 → FAIL

⇠ FAIL 时返回详细反馈具体到文件与代码行的 bug 报告,驱动下一轮修复
➜
完整应用
多小时自主构建
可运行的全栈产品
智能体之间通过 文件 通信:一个写文件,另一个读取并在文件内回复或回写新文件
三个 Agent 各自的职责与设计意图

Planner 规划者

prompt → product spec
把 1–4 句话的需求,自动扩展为有野心的完整产品规格书
  • 解决旧 harness 需要人工提供详细 Spec 的问题
  • 关注产品定位与高层技术设计,刻意不写细粒度实现 —— 避免 Spec 错误向下游级联
  • 主动在产品中编织 AI 功能(如 AI 辅助生成精灵、关卡)
  • 可读取前端设计 skill,为应用制定统一视觉语言
  • 实例:一句话 → 16 个特性、10 个 Sprint 的 Spec

Generator 生成者

spec → working code
按 Sprint 一次实现一个特性,把 Spec 变成能跑的软件
  • 沿用「一次一个特性」的范围控制策略
  • Sprint 开始前与 Evaluator 协商 Sprint Contract,明确可验证的完成标准
  • Sprint 结束先自我评估,再交给 QA
  • 收到 FAIL 反馈后针对性修复,进入下一轮迭代
  • 可根据评分趋势决定:继续打磨当前方向,还是彻底换方案

Evaluator 评估者

running app → grade & feedback
像真实用户一样操作运行中的应用,做严格、可执行的质检
  • 通过 Playwright MCP 点击真实页面,而非看静态截图
  • 测试 UI 特性、API 端点、数据库状态
  • 评分维度:产品深度、功能性、视觉设计、代码质量
  • 每个维度设硬阈值,任一不达标即整个 Sprint FAIL
  • 反馈具体到代码位置,如「fillRectangle 未在 mouseUp 触发」
  • 需专门调校:LLM 天生宽容,要把 Evaluator 调成「怀疑论者」
为什么这样设计:来自文章的关键洞察
  • 生成与评判必须分离:Agent 评价自己的作品时会「自信地夸奖平庸之作」;把干活的人和打分的人分开,再给 Evaluator 调成怀疑态度,比让 Generator 自我批评容易得多。
  • 主观质量要变成可打分标准:「这个设计好不好」无法稳定评分,「是否遵循我们的设计原则」可以。评分标准本身也会反向塑造 Generator 的输出风格。
  • 迭代产生质变:前端实验跑 5–15 轮迭代,评分逐轮上升;第 10 轮甚至出现「推翻重做」的创造性飞跃 —— 单次生成从未出现过这种作品。
  • Harness 的每个组件都是对「模型做不到什么」的假设:模型变强后要重新审视。Opus 4.6 到来后作者移除了 Sprint 结构,Evaluator 也从逐 Sprint 评分简化为最终一次性 QA。
  • Evaluator 不是固定必需品:当任务在当前模型的可靠能力边界之内,它是多余开销;只有任务处于能力边缘时,QA 才带来真实提升。
  • 成本与收益并存:复古游戏编辑器案例中,单 Agent 跑 20 分钟/$9,完整 Harness 跑 6 小时/$200 —— 贵 20 倍,但单 Agent 版本的核心功能(玩游戏)根本是坏的。
